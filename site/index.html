Has this user paid? Answer it from the store’s messages.

go-entitlements is a Go library for apps that sell subscriptions through the App Store and Google Play. The stores send your server messages about every purchase, renewal and refund. The library checks each message, puts them in order, and keeps one current record per subscription. Your code then asks one question: does this user have access.

How a subscription reaches your server

A user buys a subscription inside your app, but the money and the billing belong to the store. Your server is not in that conversation. It only learns what happened because the store calls a web address you registered, and that call is the notification.

Why you cannot trust the messages as they arrive

If your server simply did what each message says, it would sometimes grant access it should not, or take it away from someone who paid. Five things go wrong in practice.

  1. Forgery. A message must be proven to come from the store before it is believed.
  2. Duplicates. The same message can arrive many times. Applying it twice must equal applying it once.
  3. Out-of-order delivery. An older message that arrives late must not overwrite newer knowledge.
  4. Google carries no state. Its ping only says that something changed for a purchase token. You have to ask Google what the state is now.
  5. Upgrades change the identity. On Google an upgrade creates a new purchase token, so one customer briefly looks like two subscriptions.

Try it: send the messages yourself

        From a signed message to a stored answer

        Both stores end up as the same small Event: an ID, a user, a transaction, a product, a state, an expiry and the time it was signed. After that the library does not care which store it came from.

        Apple: the certificate chain is the lock

        An Apple notification is a signed token. Its header lists a chain of certificates, called x5c, that should lead to the key that made the signature. The sender writes that header. A forger can write one too. So the library does not ask whether the signature matches the certificates in the header. It asks whether the chain ends at Apple’s own root certificate, which is embedded in the library.

        Google: ask, do not believe

        A Google push is authenticated by a Pub/Sub token on the request, which the handler requires. Even then the push says only that something happened to a purchase token. The library calls purchases.subscriptionsv2.get and builds the state from Google’s answer, so a forged or replayed push cannot invent a state. A voided-purchase push is also checked against the subscription’s latest order before it refunds anything.

        The seven states

        Whatever the store calls it, each subscription is in one of seven states. Two of them grant access: active and grace, and only until the expiry date. Grace is the period when a renewal payment failed but the store is still retrying, so the user keeps access.

        Duplicates and late messages

        Every event passes the same five questions, in this order. The first two are what make redelivery safe.

        The ordering key is the time the store signed the message (signedDate on Apple, eventTimeMillis on Google), not the time it arrived. Google events dated more than five minutes ahead of the server clock are rejected, because a forged far-future time would make every genuine later event look old.

        A refund names one billing period, not the whole subscription. Apple’s transaction ID says which. The library keeps a short list of the refunded transactions on each chain. Refunding an old renewal while a newer one is paid leaves access alone. Refunding the latest one ends the chain, and a renewal of a different, later-running transaction can still bring it back even if its message arrives after the refund and was signed before it. A late message about the refunded period itself cannot.

        The duplicate check and the state change happen in one transaction. Two copies of one message arriving at the same moment cannot both apply.

        Upgrades on Google create a new token

        When a Google user upgrades or resubscribes, Play issues a new purchase token and names the old one in linkedPurchaseToken. Without care the user would hold two active subscriptions. The library applies the new chain first, then closes the old one, so there is never a moment with no active chain.

        The same works when messages go missing. Suppose token C replaced token B, which replaced token A, and only C’s message arrived. The library asks Google about B, follows B’s link to A, and retires every token it finds, up to four. If Google no longer knows a replaced token, that token is retired under its plain key. If Google cannot be reached for it, the push is answered 500 and retried.

        Add-ons: one purchase, several products

        A Google subscription with add-ons is one purchase token with several line items, and each item has its own expiry. The library stores each item as its own entitlement, so IsActive(user, product) is right for every product.

        Google needs an acknowledgement

        Google refunds a subscription that is not acknowledged within three days. When you give the Google handler an acknowledger, it acknowledges new purchases for you, but only after the entitlement is stored. If Google refuses, the handler answers 500, Pub/Sub sends the push again, the duplicate is skipped, and the acknowledgement is tried once more.

        Whose purchase is it?

        A subscription belongs to a user only if the library knows the user. Your app should set the user ID when the purchase is made. When it does not, the library still stores the purchase, keyed by the transaction, and logs a warning. There are four ways to attach the user, tried in this order.

        Two more things use the same record. WithOnChange calls your function after each committed change (a new chain, an applied event, a retired chain, a user link), which is where to flip a feature flag or tell the user. Entitlement.AutoRenew keeps the last known renewal setting from Apple’s renewal info or Google’s plan. An active chain with auto-renew off will lapse at its expiry unless the user turns it back on, which is a useful churn signal. If a store has not said, the value is unknown and is never overwritten by a message that does not say.

        Repairing a lost webhook

        Webhooks can be lost: your server was down, or a deploy dropped a request. The App Store Server API lets you ask Apple what is true now. The apple/serverapi package has two repairs. Reconcile fixes one customer. ReplayNotificationHistory re-feeds everything Apple says it could not deliver in a time window.

        Old notifications may fail verification at today’s date, because Apple’s signing certificates are short-lived. Those records are counted as failed in the report, not skipped silently. The simulator below models Reconcile. It does not model the history replay, which needs Apple’s API over HTTP and has its own tests.

        Refund requests need the customer’s consent

        When a customer asks Apple for a refund, Apple sends a CONSUMPTION_REQUEST and waits 12 hours for you to say how much of the purchase was used. You may answer only if the customer agreed to share that data. The wrapper in apple/serverapi answers these requests for you and passes every other notification to your normal handler untouched.

        What your server tells the store

        The HTTP status is an instruction to the store: stop sending this, or send it again. The rule behind it is whether a retry could change the outcome.

        One exception sits outside this table. A refund request (CONSUMPTION_REQUEST) answers 500 only while Apple’s 12 hours are running, and 200 once they have passed.

        One thing is left to you: the user ID. The library takes it from appAccountToken (Apple) or obfuscatedExternalAccountId (Google), which your app sets at purchase time. Treat it as a hint from the client, not as authentication.

        Storing the result: one contract, two stores, yours

        The library ships a memory store and a Postgres store. To use another database, implement the Store interface, which has twelve numbered rules, and run the conformance suite against it.

        How it was tested

        Numbers below come from the repository’s Definition of Done file, which records what was measured and when.

        9,600deliveries across 64 goroutines in the heavy stress run, with supersedes crossing each other
        1,996/son Postgres with 20 connections; 523/s with 2. Memory store: about 40,000/s or more
        30 sof fuzzing per target for both parsers and the state machine, with no crashers
        5real signed notifications from a live app: one Production TEST, four Sandbox
        • Unit and integration tests run with -race. Integration tests use real Postgres 17 through Docker, and an end-to-end test drives HTTP, service and Postgres together.
        • Apple payloads in tests are signed by a generated CA, so the full verification path runs. Apple’s own library test tokens also verify.
        • The simulator on this page is checked against the library on every push. Over 240 recorded steps in about 60 scenarios are replayed through the real parsers, handlers and service on one side and through the JavaScript port on the other, and CI fails if they disagree.
        • Mutation testing with gremlins (make mutate) was used to find and kill surviving mutants. It is not part of CI and no score is published.
        • A tampered copy of a real notification is rejected with 401.
        • The Server API client was run against the live Apple Sandbox for one app: a TEST notification and 4 history records verified, a Reconcile that applied and then reported unchanged, and a replay that applied 3, ignored 1 and failed none.
        • The tests were also run against issues reported on other subscription libraries, listed in docs/prior-art.

        What is not verified. The five real Apple notifications and the live Sandbox run come from a private app. The notification files are not in the repository, so nobody else can reproduce that run, and the test skips when they are absent. The Google side has never been run against live Play traffic. Its tests use fixtures taken from Google’s documentation and public issues, with the Play API mocked, and the acknowledge call is tested against a local fake of the Play API. The refund-request answer has not been sent to the real Apple API.

        Quickstart

        Requires Go 1.26. Install with go get github.com/tggo/go-entitlements. These snippets are compiled as Examples, and a test fails if the README drifts from them.

        Apple only, in-memory store

        ctx := context.Background()
logger := slog.Default()

svc := entitlements.NewService(memory.New(), entitlements.WithLogger(logger))

verifier, err := apple.NewVerifier("com.example.app", // the bundle ID is required
	apple.WithEnvironment(entitlements.EnvironmentProduction)) // reject Sandbox and TestFlight
if err != nil {
	log.Fatal(err)
}
mux := http.NewServeMux()
mux.Handle("/webhooks/apple", httpx.NewAppleHandler(apple.NewParser(verifier), svc, httpx.WithLogger(logger)))
go func() { log.Fatal(http.ListenAndServe(":8080", mux)) }()

// Later, in your own handlers: does this user have access?
ok, err := svc.IsActive(ctx, "7e3fb20b-4cdb-47cc-936d-99d65f608138", "com.example.pro.monthly")
if err != nil {
	log.Fatal(err)
}
log.Println("has access:", ok)

        The same service on Postgres

        ctx := context.Background()
logger := slog.Default()

pool, err := pgxpool.New(ctx, os.Getenv("DATABASE_URL"))
if err != nil {
	log.Fatal(err)
}
defer pool.Close()
store := postgres.New(pool)
if err := store.Migrate(ctx); err != nil { // idempotent, safe from several instances
	log.Fatal(err)
}
svc := entitlements.NewService(store, entitlements.WithLogger(logger))

list, err := svc.ListByUser(ctx, "7e3fb20b-4cdb-47cc-936d-99d65f608138")
if err != nil {
	log.Fatal(err)
}
for _, e := range list {
	log.Println(e.ProductID, e.State, e.ExpiresAt)
}

        Google Play

        Create a Pub/Sub push subscription that sends an OIDC token. The audience is the endpoint URL and the service account is the one you pass to pubsubauth.New. The service account behind androidpublisher.NewService needs permission to view financial data for the app in the Play Console, and to acknowledge purchases.

        ctx := context.Background()
logger := slog.Default()
svc := entitlements.NewService(memory.New(), entitlements.WithLogger(logger))

playAPI, err := play.NewService(ctx) // credentials from GOOGLE_APPLICATION_CREDENTIALS
if err != nil {
	log.Fatal(err)
}
fetcher := androidpublisher.NewFetcher(playAPI)
parser, err := google.NewParser(fetcher, "com.example.app")
if err != nil {
	log.Fatal(err)
}
// The Pub/Sub push subscription must send an OIDC token for this audience
// and service account; the handler refuses to start without a check.
auth, err := pubsubauth.New("https://example.com/webhooks/google", "push@my-project.iam.gserviceaccount.com")
if err != nil {
	log.Fatal(err)
}
// WithAcknowledger acknowledges new purchases once they are stored; Google
// refunds purchases that are not acknowledged within 3 days.
handler, err := httpx.NewGoogleHandler(parser, svc, httpx.WithLogger(logger),
	httpx.WithPushAuthenticator(auth), httpx.WithAcknowledger(fetcher))
if err != nil {
	log.Fatal(err)
}
http.Handle("/webhooks/google", handler)

        Attach users, react to changes, erase

        ctx := context.Background()
logger := slog.Default()

svc := entitlements.NewService(memory.New(),
	entitlements.WithLogger(logger),
	// Path 1: look the user up when an event arrives without one, for example
	// in your originalTransactionId -> user table. An error makes the store retry.
	entitlements.WithUserResolver(func(ctx context.Context, ev entitlements.Event) (string, error) {
		return lookupUser(ctx, ev.Source, ev.OriginalTxID) // "" if unknown yet
	}),
	// React to a committed change, e.g. to tell the user or flip a feature flag.
	entitlements.WithOnChange(func(ctx context.Context, before, after *entitlements.Entitlement) {
		logger.InfoContext(ctx, "entitlement changed", "user", after.UserID, "state", after.State)
	}))

// Path 2: the app reports the purchase right after it happens. This is
// idempotent; a chain that already belongs to another user returns
// entitlements.ErrUserConflict and is never reassigned.
_, err := svc.LinkUser(ctx, entitlements.SourceApple, "2000000000001", "user-42")
if errors.Is(err, entitlements.ErrUserConflict) {
	log.Println("this purchase belongs to another account")
}

// Erasure request: delete the user's entitlements and stored payloads.
if _, err := svc.ForgetUser(ctx, "user-42"); err != nil {
	log.Fatal(err)
}

        Repair a lost webhook

        ctx := context.Background()

key, err := os.ReadFile("AuthKey_ABC123DEFG.p8")
if err != nil {
	log.Fatal(err)
}
client, err := serverapi.New(serverapi.Config{
	IssuerID:      "57246542-96fe-1a63-e053-0824d011072a",
	KeyID:         "ABC123DEFG",
	PrivateKeyPEM: key,
	BundleID:      "com.example.app",
	Environment:   entitlements.EnvironmentProduction,
})
if err != nil {
	log.Fatal(err)
}
svc := entitlements.NewService(memory.New())

// 1. A customer says they paid but have no access: ask Apple.
results, err := serverapi.Reconcile(ctx, client, svc, "2000000000000001")
for _, r := range results {
	fmt.Println(r.Event.OriginalTxID, r.Outcome)
}
if err != nil {
	log.Print(err)
}

// 2. After an outage, re-feed every notification Apple could not deliver.
verifier, err := apple.NewVerifier("com.example.app", apple.WithEnvironment(entitlements.EnvironmentProduction))
if err != nil {
	log.Fatal(err)
}
report, err := serverapi.ReplayNotificationHistory(ctx, client, apple.NewParser(verifier), svc,
	time.Now().Add(-48*time.Hour), time.Now(), serverapi.ReplayOnlyFailures())
fmt.Printf("applied %d, duplicates %d, stale %d, failed %d\n", report.Applied, report.Duplicate, report.Stale, report.Failed)
if err != nil {
	log.Print(err)
}

        Answer refund requests

        var (
	client   *serverapi.Client // from serverapi.New
	verifier *apple.Verifier   // from apple.NewVerifier
	next     http.Handler      // httpx.NewAppleHandler(parser, svc)
)
responder := serverapi.ConsumptionResponderFunc(func(ctx context.Context, req serverapi.ConsumptionRequest) (serverapi.ConsumptionInfo, error) {
	consented, err := lookUpConsent(ctx, req.UserID, req.OriginalTransactionID)
	if err != nil {
		return serverapi.ConsumptionInfo{}, err // transient: Apple redelivers
	}
	if !consented {
		return serverapi.ConsumptionInfo{}, serverapi.ErrConsentRequired // nothing is sent
	}
	return serverapi.ConsumptionInfo{
		CustomerConsented:     true,
		DeliveryStatus:        serverapi.DeliveryDelivered,
		SampleContentProvided: true,
		RefundPreference:      serverapi.RefundDecline,
	}, nil
})
http.Handle("/apple", serverapi.NewConsumptionHandler(next, serverapi.ConsumptionHandlerConfig{
	Verifier: verifier, Responder: responder, Sender: client,
}))

        The service has Process (used by the handlers), IsActive, Get, ListByUser, LinkUser and ForgetUser.

        Known limitations

        Status: v0. The core, both parsers, the in-memory and Postgres stores and the HTTP handlers are tested end to end, but the API may change between minor versions until v1. Changes are listed in the release notes.

        • Google: a subscription with add-ons is stored as one entitlement per line item (purchaseToken#productId). A purchase with a single item keeps the plain purchaseToken key. When a purchase gains or loses an add-on, the row under the old key shape is not rewritten and ends at its own stored expiry; immediate item-based revocation is not tracked.
        • go.mod says go 1.26.0, not 1.26: the Google API dependencies require it.
        • Privacy: the Postgres store keeps each webhook body in processed_events.raw so that events can be audited. It can contain account identifiers; call Store.Prune on a schedule, and Service.ForgetUser for an erasure request (it clears the payloads of that user's chains and deletes the entitlements, keeping event IDs so redelivered webhooks stay duplicates).

        Not in scope. Legacy verifyReceipt, Stripe and other web payment providers, and consumables.
